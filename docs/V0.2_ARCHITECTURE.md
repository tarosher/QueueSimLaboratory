# QueueSimLab V0.2 — Revised Architecture and Implementation Baseline

**Revision date:** 2026-10-26  
**Project:** MATLAB-based reusable queueing discrete-event simulation  
**Scope decision:** build queueing networks in V0.2; reserve interface contracts for resources, traffic/congestion and EV/energy.  
**Implementation checkpoint:** M1 MATLAB R2022b test suite passed per user confirmation. M2 implementations authored, MATLAB M2 runtime validation pending.

## 1. Purpose and extensibility principle

QueueSimLab's core is a discrete-event kernel that executes configurable arrival streams, queue mechanisms, server/resource accounting and outputs statistically interpretable results. The engineering abstraction is `Entity → Source → Queue/Service Node → Route → Sink`, with an event calendar, persistent identifiers and observation hooks.

Four complementary complex-model families share the same core and integrate through versioned namespaces and registered handlers:

| Extension family | High-level modeling purpose | V0.2 scope | Contract |
|---|---|---|---|
| **Queueing networks** | Multi-stage service nodes, serial/parallel/merge topology, routing decisions, bottlenecks | **Selected for implementation in M4** | `network` |
| **Resource-constrained systems** | Shared staff, machines, forklifts, resource acquisition/release and schedules | **Reserved only** | `resources` |
| **Time-varying traffic/congestion** | Demand fluctuation, finite physical storage, queue spillback, road capacity | **Reserved only** | `traffic` |
| **EV charging and energy** | Battery SOC, charging curves, shared power caps, continuous/discrete coupling | **Reserved only** | `energy` |

Rationale: Queueing networks are a direct generalization of the original supermarket queueing simulation. Other complex scenarios become optional adapters over the common network/resource structures after they are validated; specifically, EV charging **is not** a V0.2 benchmark or implementation requirement.

`qsim.extensions.registry()` lists these reserved extension keys. This **does not mean they currently run**; M1 explicitly rejects enabled extension flags. All four contracts are described in `EXTENSION_CONTRACTS.md` with expected event/data and invariant hooks.

## 2. V0.2 definition of done

| Layer | Deliverable by V0.2 | Not part of V0.2 |
|---|---|---|
| Core events | Clock, deterministic event tie order, future event calendar, reproducibility, event guard | Distributed / real-time simulation |
| Arrivals | Poisson, explicit schedules, piecewise Poisson, extensible renewal profiles | OD demand inference |
| Queue nodes | M/M/1, M/M/c, M/G/1, G/G/c and finite-capacity variants configured via one engine | Preemptive priority, fork/join |
| Queue policies | Shared FIFO, independent lines, probability, shortest line, estimated queue workload | Learned RL routing policies |
| Networking | Directed node graph, tandem/parallel/merge routes, transfer delays, visit tracing | Upstream spillback/backpressure and fork/join synchronization |
| Statistics | Time-weighted occupancy, cohort-aware waits, independent replications and paired confidence intervals | Claiming independent CI for unrandomized QMC |
| Visualization | Queue/server history, strategy comparison, network bottleneck and load/topology diagrams | GUI and network editor |
| Other extensions | Reserved names, configuration/API hooks, explicit rejection until implemented | Physical traffic flow / power flow / SOC integration |

**Release gates:** reproducible quick start from clean clone; base MATLAB engine; benchmark triad; validated theory and core invariants; accurate documentation; optional toolbox requirements for randomized QMC disclosed, source licensing established.

## 3. Three benchmark experiments (revised)

1. **A: Queue strategy comparison** — With identical arrival cohorts, service requirements and total service capacity, compare probabilistic independent lines vs pooled FIFO vs estimated-wait independent lines. Keep shortest line as an optional fourth strategy. Report mean/P95 wait, average queue, utilization and paired CIs. Never use unknown future service times as a policy oracle.
2. **B: Multi-stage bottleneck experiment** — A → B1/B2 → C network. Compare allocating one additional server to different nodes. Report per-node queue waiting, end-to-end sojourn, throughput and bottleneck effects. Document graph and transfer semantics.
3. **C: Network topology and load stress** — Compare serial versus parallel routing/merging layouts, traffic allocation probabilities and off-peak/peak time-varying arrivals, using the **same generic queue-network engine**. Examine congestion propagation at a modeling level of queue-node performance, **not physical road spillback**.

Three experiments are reproducible scripts, with source configs and figures, NOT merely static illustrations. Experiment C has no EV or electricity model.

## 4. Mathematical foundation

An event-driven state is

\[
X(t)=[\text{entities},\text{queues},\text{servers},\text{FEL},\text{network},\text{observations}].
\]

At the next event time \(t_k\), update the system via \(X(t_k^+)=\Phi(X(t_k^-),e_k,\theta,\xi)\). Between events, queues and server counts are piecewise constant and integrate exactly for time-weighted averages.

At a service node with arrival rate \(\lambda\), mean service rate per identical server \(\mu\), and \(c\) servers, a steady homogeneous M/M/c has \(\rho=\lambda/(c\mu)\). Distinguish per-entity/visit waiting \(W_q=t_{start}-t_{arrival}\) from end-to-end sojourn and time-average queue \(\overline{L_q}=\int_0^T Q(t)dt/T\). For steady open networks, nominal traffic equations satisfy \(\boldsymbol\lambda=\boldsymbol\gamma+P^\top\boldsymbol\lambda\) under the usual stability/no-loss assumptions; DES does not require a product-form solution.

All time is represented in **minutes** in the V0.2 core. `arrivalHorizon` determines the last new arrival; `observationHorizon` defines integral statistics; `stopMode='drain'` continues accepted jobs after that horizon, whereas `truncate` leaves explicit backlog and produces censored observed-cohort stats. For networks, separate visit logs from entity-wide lifecycle records.

### Simultaneous event policy

At the same timestamp (within a configured tolerance): completions first, then arrivals/transfers, then stable insertion order. At node-network maturity, service dispatch and transfers will be standardized in microstep phases for deterministic, policy-neutral resource allocation. Later dynamically reschedulable events will require version tokens; these are **future hooks**, not current M1 behavior.

### Capacity semantics

Eventually accept `maxSystemOccupancy` (queue + active service) and `maxWaiting` separately. M1 rejects finite capacities; later network buffers without room will reject the arriving entity with explicit reason/count. Upstream backpressure/spillback remains out of scope for V0.2.

## 5. API baseline

Main entrypoint:

```matlab
Config = qsim.defaultConfig();
Results = qsim.run(Config);
```

Frozen top-level fields: `version`, `simulation`, `source`, `network`, `randomness`, `extensions`, `output`. The full stable **shape** is described below; M1 supports only a restricted single-node subset.

| Configuration namespace | Fields / conventions |
|---|---|
| `simulation` | `arrivalHorizon`, `observationHorizon`, `stopMode`, `seed`, `tolerance`, `maxEntities`, `maxEvents`, `warmup`, `nRep` |
| `source` | `type`, `rate` or `times`; future extra time profiles |
| `network.nodes` | `id`, `nServers`, `queueMode`, `serviceDistribution`, `maxSystemOccupancy`, `maxWaiting` |
| `network.links` | Future endpoints, transition probabilities and delays |
| `randomness` | `method='PRNG'`; randomized low discrepancy sequences later |
| `extensions` | logical flags named `network`, `resources`, `traffic`, `energy` |
| `output` | `retainEntityRecords`; future detailed visit / event logs |

Historical M1 working subset: one node, pooled FIFO, 1+ servers, Poisson or scheduled arrivals, exponential/deterministic/explicit sequence service durations, no finite queue capacities, PRNG and two stop modes. No network links or enabled complex-model extensions. Do not mistake the frozen interface shape for full V0.2 functionality.

Results hold `system`, `nodes`, `entities`, `reproducibility`. Future extensions add `visits`, `routes`, `resources`, `traffic` or `energy` without changing the base result names. The network extension will preserve the core per-entity unique IDs and add distinct per-visit IDs.

## 6. Statistics and reproducibility

- **PRNG:** fix seed per independent replication and label it. Do not use fixed 1,000-row matrices that inadvertently cap demand.
- **CRN future experiments:** align *arrival IDs and service requirements by entity/visit*, not server random-draw positions, otherwise policy changes break meaningful pairing.
- **Randomized QMC:** Sobol and Halton retained in original code but only reintroduced with independent scramble/replication semantics and any needed toolbox disclosure.
- **Observations:** report waiting time for full arrival cohort after drain, or explicitly label incomplete/censored started-service cohort in truncate mode. Observation window denominators must be documented.
- **Baseline checks:** M/M/1 mean wait \(W_q=\lambda/[\mu(\mu-\lambda)]\); M/M/c Erlang-C \(W_q=P(\text{wait})/(c\mu-\lambda)\), \(\rho=\lambda/(c\mu)\), \(L_q=\lambda W_q\).
- **Conservation:** `arrived = completed + rejected + backlog` for supported loss and termination semantics. Queue/server time integrals nonnegative, no negative waits, monotonic time.
